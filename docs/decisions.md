## 2026-08-13: router scrolls opt out of smooth scrolling

Clicking between pages landed short of the top while pasted URLs landed clean. Next 16 stopped suppressing CSS `scroll-behavior: smooth` during its scroll-to-top on navigation unless the html element carries `data-scroll-behavior="smooth"`; without it the scroll became an animation whose own follow-up check cut it short around the masthead's height. The attribute now sits on the html element in the locale layout, and smooth stays for in-page anchor jumps, which never enter the router. Two guardrails for future work. Never add `scroll-padding-top` to html: the router reads it for its in-viewport check and it reintroduces the same landing-short bug even with the attribute present; per-target `scroll-margin-top` is the house pattern. And browser tests must scroll with `behavior: "instant"` in setup steps, because plain `window.scrollTo` animates under the smooth rule and a click mid-animation measures garbage.

## 2026-08-13: the app owns its navigation glide

Making router scrolls instant (earlier today) fixed the landings but killed the glide the owner wanted, and Next has no supported smooth navigation scroll: the issue asking for one (#51721) was closed by the PR that added the suppression. So the app owns the animation. The Link that everything imports from i18n/navigation wraps the next-intl Link with Next scrolling off; a plain primary-button click on it records one glide intent (destination pathname, search, hash), and a same-document destination glides immediately, which is how the wordmark at home and the active masthead tab return to top. ScrollGlide, mounted once in the locale layout behind Suspense, lets the first route commit consume the intent, and only a commit matching the intent's URL glides, animating to the hash target or the top; a mismatched commit (a superseded click, a redirect) just drops it. Back and forward, the Explorer's replaceState writes and the locale switchers record no intent, so browser restoration and keep-your-place survive untouched. That intent gate is load-bearing: installed Next 16.3 mirrors external replaceState into useSearchParams (its patched history dispatches a restore action), so a manager reacting to route keys alone would glide on every search keystroke. The html attribute and the CSS smooth rule stay: native in-page anchors keep their animation, and any navigation that slips past the wrapper lands instant and correct rather than animated and short. Readers with reduced motion get instant scrolls through a media query the glide helper also respects. Verified headless on the production build: twelve-case matrix asserting animated trajectories frame by frame, exact landings, quiet back button, kept locale-switch position, one real playback.

## 2026-08-18: samples arrive compressed, and expiry stops being reinvented per layer

Measured on the live site, a click took 3.3 seconds to make a sound: the signed-URL call was about a third of a second of that and the rest was fetching a 460KB WAV. The upstream service had been storing an Opus (48 kbps) and an AAC (96 kbps) preview of every ready sample all along, made by a conversion task and swept in by a backfill every fifteen minutes, but its API v1 sample endpoint passed a hardcoded `undefined` where the caller's format preference goes, so `selectBestFormat` fell to WAV for every API caller. Its own `/voices` grid gets compressed audio only because it calls a different, browser-authenticated door that does forward the preference. The owner had the API side changed to accept an ordered `?formats=` (committed there as a60b66021, spec deliberately left frozen while the parameter has no external consumers), and Speakshelf now asks: Safari for AAC then WAV, since it decodes AAC in MP4 natively, every other engine for Opus then AAC then WAV, probed once per session. WAV always ends the list, so a voice whose preview has not been converted yet still plays.

Three things fall out of that and are now invariants. A ready URL is format-specific, so the server caches and coalesces it under voice, sub-model and format together: one process serves a Safari visitor and a Chromium visitor, and sharing an in-flight lookup between them would hand one of them audio it cannot play. Generation is not format-specific, since upstream synthesizes one sample per voice and converts it afterwards, so the "still generating" answer stays keyed by voice and sub-model, without the format, and every retrier of a cold voice, whatever format it wants, still collapses into one upstream lookup per retry interval and one miss token. And a compressed request that comes back as WAV is cached for ten minutes rather than a day, because that answer means the conversion has not run yet and a long hold would pin the voice to the large file long after the small one appeared.

The same change closed a bug that had been shipped for weeks and was found while reasoning about the first one. Signed URLs live 24 hours upstream; the server kept one for 20 and the browser then kept it another 18 counted from when it arrived, so a URL handed over late in the server's window could be treated as fresh by the browser well past its death, surfacing as one "sample unavailable" before the retry recovered. Upstream reports an absolute expiry and always did; we were dropping it. The server now trims an hour of safety off that moment, caps it at the old ceiling for an upstream that ever stops reporting, and passes the result to the browser as `reuseUntil`, which expires its copy against the same moment. No layer restarts an expiry clock from when it received a URL.

## 2026-08-18: five defects the format round exposed, and the deadline the player never had

The owner reported that playback froze at random and that filtering the Gemini family made the toolbar flash, and he was right that a working implementation existed to copy and that we had not copied all of it. What the audit actually found, after running both builds side by side on one machine against the same upstream, was that the flashing was NOT introduced by the format change: the same page, the same clicks, gave 2.95s filter time, the same 386ms blocking task and the same toolbar churn on both. The genuine faults were five, and only two of them were new.

Mine and new: the generating marker was consulted before the ready cache, so a voice whose URL was already cached could be told "still preparing" for the marker's whole life, up to fifteen seconds. The marker is now read only on a genuine miss, and a ready answer clears it. Also mine, and the cause of the severe window the owner first hit: while the API half was deployed and ours was not, every request asked for a compressed format, got WAV, and took the ten minute fallback, which collapsed the whole site's cache from about nineteen hours to ten minutes and re-minted every voice against a budget of roughly seven hundred an hour. Those entries expire on their own and the path is correct once compressed audio is really served, so nothing was changed for it beyond writing the trap down.

Not new, and never copied from the reference player: the media load had no deadline at all. The lookup's abort covers the URL request only, so an element that neither started nor errored, which is exactly what a stalled range request looks like, left the row spinning forever with no way back. It now carries a twenty second deadline armed before `play()`, and every other wait the chain can schedule, the retry interval and the request abort included, is clamped to what remains of the reader's ninety seconds, so that budget is terminal rather than aspirational. Proven by hanging every audio request in a real browser: the row recovered in 20.2s saying "sample unavailable" instead of never.

Also never copied: per-row memoization. Thousands of rows sit under the component that owns playback state, each previously receiving a freshly minted callback, so changing one row reconciled all of them. Rows are memoized with a comparator and the list now passes one shared handler, routed through a ref refreshed after each commit so it cannot capture a stale sub-model or active row. Filtering the Gemini family went from 2.95s to 1.66s and its worst main-thread block from 386ms to 139ms. Virtualization was considered and rejected: the reference uses a fixed-height windowed grid, but this list is sectioned per language with sticky heads and `content-visibility` containment, which such a grid would fight. The owner made that call and it is the right one.

Last, the analytics were blind. A change whose entire subject is the audio format shipped without recording which format anyone received or how long a play took, so when the owner said it was broken neither side could answer with data. `sample_played` now carries the served format and the click-to-sound duration, `sample_failed` carries the format where one was served, and both derive the format from the server's `contentType` rather than from what the browser asked for. The format-specific cache key is kept as it is: a browser sends one of four preference strings, so the extra cold lookups are bounded, and correctness beats saving a token.

## 2026-08-18: the player fetches small samples instead of streaming them

Measured on production, with the same five voices and the sample cache pre-warmed so neither engine paid for a cold mint, a first play took a median of 958ms on Chromium and 4050ms on WebKit. The gap was not the API, which answered in under a second for both. It was the media element: handed a URL, WebKit opened four requests for one sample, three ranges and then the full file, before it would make a sound. An in-page experiment on the same signed URL pointed the way: assigning the URL reached playing in 2706ms on WebKit against 667ms for fetched bytes. It also showed a large Chromium gap, 1739ms against 892ms, which did NOT survive a proper test: an alternating same-session A/B over fourteen plays per arm found Chromium indifferent (452ms bytes against 425ms streamed) and Firefox likewise (444 against 443), fourteen plays per arm in each. WebKit could not be tested that way at all: it refuses play() without a user gesture, so only four of fourteen bytes plays and two of fourteen streamed plays ever fired, and that arm is excluded rather than reported at its flattering ratio. The Safari conclusion rests on the end-to-end click measurements instead. The isolated experiment had measured an audio element with the URL already in hand, not a reader's click, and it should not have been read as evidence about Chromium.

So compressed samples are now fetched whole and played from memory, and the WAV fallback keeps streaming, where progressive playback of a 460KB file still earns its keep. Measured after deploying: WebKit's median first play fell from 4050ms to 2126ms on desktop, 1953ms on mobile, and Chromium stayed where it was, around 1000ms, once repeated runs separated the signal from a single noisy sample that had briefly looked like a 400ms regression. The decision keys off the format the server actually served, never off the browser, because the browser's preference is not evidence of what arrived. This became possible only because samples are compressed now: downloading 460KB before making a sound would have been a regression, which is very likely why the reference player streams first and warms afterwards, a shape it has carried since its own WAV era.

The same change removes a transfer nobody needed. The old path streamed the sample and then, once playback was confirmed, fetched the whole file again to fill the replay caches; the reference's comment calls that "one network request total", which assumes the browser serves the second fetch from its own cache, and our measured waterfall showed it did not. One fetch now feeds playback, the blob tier and the decoded tier together. Measured after the change: exactly one request per first play in both engines, and none on replay.

Two hazards were found in review and closed before shipping. A blob that fails must not be rebuilt by the warm that follows its fallback, so warming is marked handled the moment recovery starts. And recovery had to cover every way an object URL can fail, not just the element's error event: a media deadline or a play() rejection on a poisoned blob would otherwise have ended the attempt, leaving the reader with no audio where plain streaming would have worked. Both now route through one guarded fallback that drops the suspect bytes and streams instead. Proven by serving deliberate garbage in place of the audio in both engines: playback recovered and played rather than failing. Two lifecycle edges came out of the same review. A decode already running when the bytes are discarded would have written its result back afterwards, restoring audio the player had deliberately thrown away, so decoded entries now carry a generation that a finishing decode must still match, and replacement bytes never wait on the outgoing blob's decode. And a blob outlives its signed URL as a matter of course, since the two tiers have different lifetimes, so recovery mints a fresh URL rather than declaring the sample gone.

Preparation failures got their own event. A bytes fetch that falls back to streaming costs the reader nothing, and a decode failure only downgrades the next replay, so neither belongs in `sample_failed`, which means the reader heard nothing. They are `sample_prepare_failed`, carrying the stage and elapsed time, deduplicated per voice per session.

One thing deliberately NOT done. The reference keys its replay caches by voice and sample version. Speakshelf has no version, and an audit of the upstream service found the value is a constant: every sample document is created with 1, nothing increments it, and regeneration bumps a heal counter instead, so the reference's key is effectively voice-and-one. Relaying it would have bought nothing. The real gap, that a regenerated sample cannot be distinguished from the one a tab already cached, needs a generation epoch in the service and is recorded there as MF-037 rather than approximated here.

## 2026-08-19: the replay tier must prove the context is awake

The owner found it on iOS Safari within a day of the bytes path shipping: the first play of a voice sounded, and the second tap moved the equaliser in silence. Desktop was fine. The cause was ours and it was subtle. Replays come from decoded audio through a Web Audio context, and that context was resumed with a fire-and-forget call before the source was started. On a desktop context that is already running the race never shows. On iOS it always loses, because a context created without a gesture starts suspended, `resume()` is a promise, and a source started before it settles plays into a sleeping context: silence, behind a UI that has already declared success.

What exposed it was the previous round's own change. Decoding used to happen after confirmed playback, so the context was first built once a media element had already made sound from the reader's tap and iOS had unlocked the page's audio. Moving the decode ahead of playback, to have the replay tier ready sooner, meant the context was now built inside a fetch promise with no gesture and no prior sound. A clean win on paper, a regression on a real phone.

Two corrections, together. The decoded tier now plays only through a context that reports itself running: an asleep or `interrupted` context (Safari's own state after a call or another app takes the session) is woken and re-checked against a 1.5 second deadline, and a context that will not wake is treated as a tier miss rather than a failure, so the play falls through to the blob tier and a media element, which needs no context at all. The decoded bytes are kept, because what failed was activation, not the audio. And decoding is restored to confirmed playback, so nothing builds a context before the first sound of a session.

Proven by simulating exactly what iOS does when it refuses: a context whose state never leaves suspended and whose `resume()` never settles. Before, that is a silent replay; after, the replay falls through and the media element plays for a second time, in both Chromium and WebKit.

Worth recording about the reference, since it was the model for this tier: it carries the same fire-and-forget resume before `source.start()` and is protected only by ordering, never creating its context before first sound. Copying its structure would have hidden this bug rather than fixed it.

## 2026-08-23: the sitemap regenerates daily and stops publishing a date

Production was serving a sitemap generated once, at build, from the committed fallback catalog. Every one of its 2,072 entries carried `lastmod 2026-08-13` while the pages themselves reported the catalog as refreshed on 2026-08-23, and `.next/prerender-manifest.json` gave `/sitemap.xml` an `initialRevalidateSeconds` of `false` against `86400` for `/llms.txt`. A generated sitemap is a route handler Next caches, and `app/sitemap.ts` was the one catalog-derived route that never declared a window, so it was prerendered once and served from that artifact.

The frozen date was the visible half. The frozen URL SET was the half that matters: the route derives one entry per provider and one per language from the catalog it saw at build, so a language appearing upstream could not enter the sitemap until the next deploy. Nothing was missing on the day this was found (live and fallback agreed exactly, 93, 42 and 9 languages), which is why it read as a date problem rather than a coverage one. Language pages carry `dynamicParams = true` and the provider language index revalidates daily, so such a page would still have been reachable, just undiscovered in the sitemap.

Two proofs that the build took the fallback path rather than simply refreshing on the 13th: `lib/catalog.ts` stamps `updated` with the local date when a live fetch succeeds, never with an upstream one, and copy committed on the 16th is live on production. A successful fetch during that build could not have produced the 13th.

So the route now says `revalidate = 86400` like its neighbours, and `lastModified` is gone rather than corrected. The only date available is that same `updated` field, which moves on a successful REFRESH and not on a change: the live payloads were byte-identical to the 13 August fallback while the footer read 23 August. Publishing it would tell crawlers all 2,072 URLs changed on one day, every day the fetch worked. A deploy timestamp is no more truthful. An honest per-page date needs real change detection, which this does not have, and lastmod is an optional field. `changeFrequency` and `priority` stay: Google ignores both, they are valid, and removing them would be churn.

Worth noting for whoever adds the next generated metadata route: the missing window was invisible locally, because a dev server regenerates on every request. It only shows on a deployed artifact.

## 2026-08-23: the query string and the filters stop driving each other

The owner opened `/ja/google?family=Neural2` and `/bn/google?family=Studio` and reported flashing. Two separate faults were behind it, and the second was much worse than it first looked.

The filter fault. The Explorer started with five empty fields and applied the URL in an effect. That effect also flipped the `urlApplied` guard, and the writer effect, running later in the SAME commit but still closed over the first render's empty values, published an empty query over a real one. Next mirrors an external `replaceState` back into `useSearchParams`, so the emptied URL echoed in, the applier adopted it, the writer republished, and the two chased each other. The old comment claimed the echo could not loop because it carried the values already applied; that was wrong, because it carried the values from the opposite render.

On an unthrottled desktop it settled in two flips and nothing showed, which is why the first diagnosis called it cosmetic and said the list never painted unfiltered. Under a six times CPU throttle, a slow-client probe rather than any particular device, it did not settle at all: three runs each flipped the query eight to ten times, painted the whole 4,586 voice catalog in place of the 62 Neural2 voices three times, and were still alternating at twenty two seconds, ending on the wrong list. The review caught the overclaim and the throttled measurement is what proved it.

The rewrite lives in `lib/filter-url.ts` rather than in the component, because this is a state machine and running it as two loose effects next to a playback engine is how it went wrong. One string records the query both sides agree on: a navigation is adopted only when the URL differs from it, a write happens only when the state differs from it, and anything equal to it is our own echo and is dropped. The URL is parsed during the first render through a lazy state initializer, so there is no window in which empty fields are the truth. The writer stands down for exactly one pass while an adopted navigation lands, which is sound only because the writer's dependency list is a superset of the adopter's, so that pass is guaranteed to happen; that is why `subModels` appears in both. A value the catalog disowns is cleared by derivation, never by a correcting effect. The raw snapshot still holds whatever the URL said, but a rejected value is never exposed as an effective filter and is never written back to the address, so no render shows the wrong list and the writer cannot republish it. A field the reader changed while the catalog was loading survives without needing the old touched-field heuristic; the adopter does replace a whole snapshot, but only for a router navigation the reader caused, where the incoming URL is meant to win. Writes are skipped when `pathname + search + hash` already reads that way.

Measured after: zero query flips at one times and at six times throttle, the unfiltered list never paints, and the page settles on 62 rows. ## 2026-08-24: a control the reader used before the page woke up is honoured

Found while verifying the previous deploy on production, and it predates all of it: the language-page toolbar has been server-rendered and controlled since the first Explorer on 2026-08-13. Those pages ship the search box and the select fields in the HTML, so they look usable before React attaches, and anything done in that window was silently discarded. The control kept showing the reader's choice and the list never acted on it, permanently: the box read "achernar" while all 71 rows stayed. Reproduced on production in Chromium with real keyboard input, and on the gender select as well, so it was never only the search box. The language select is not rendered on a route-locked page, so the affected controls are search, family, gender and the sub-model picker.

The reader's choice was never actually gone. React 19 deliberately does not overwrite a live input or select while hydrating: `initInput` receives `isHydrating` and skips the value assignment, and the select hydration branch attaches metadata without calling `updateOptions`. The browser still held the value; the application simply never asked for it. So `ExplorerCore` now asks, once, in a layout effect, as one state update. One update rather than one per control, though not because separate calls would clobber each other: `patch` merges functionally and they would not. Because the toolbar's fields are one answer, and reading them in one pass is the only version of this that does not lean on React batching or on the order two effects happen to run in. A layout effect rather than a passive one, because refs attach at commit and this runs before the next paint, closing the window in which a controlled re-render would enforce the stale state and wipe what the reader did.

Three alternatives were weighed and rejected. Disabling the controls until hydration is honest and depends on no React behavior, but it makes a fully rendered page inert for seconds on a slow connection, locks out keyboard and assistive users while it waits, and throws the interaction away rather than keeping it. Making the controls uncontrolled would trade one source of truth for imperative reads across two mounts, clear-all, the badge counts and the provider-page URL writer. Not server-rendering the toolbar at all would remove the window but cost the no-JavaScript rendering and the crawler-visible structure that the language pages exist to provide, and would need an equal-sized placeholder to avoid a jump, which is the disabled option again in another shape.

The honest limit: this relies on behavior verified in the pinned React 19.2.8 implementation, not on a documented public guarantee that user-mutated form properties always survive hydration. That is acceptable because the version is pinned and the behavior is deliberate rather than incidental, and it is exactly why the regression test is the shape it is. The test holds the component chunks behind a gate rather than sleeping: the held gate is itself the proof that no handler could have run, and every case asserts both halves, that the control keeps the value AND that the rendered rows really changed to match. Where a property of the rows can be checked it is checked rather than counted: the search case reads the surviving names, and the combined case asserts every remaining row carries both the chosen family and the chosen gender. Covered in Chromium, WebKit and Firefox: search; family and gender changed together; survival across later renders and clear-all afterwards; narrow width; a wide choice carried into the mobile panel's second field mount after a resize, which is the only check that proves the panel reads reconciled state rather than raw DOM; a non-default sub-model, asserted three ways, that the picker keeps it, that the row's model text reads exactly the picker's own label rather than merely reading something, and that the model parameter of the sample request carries it, fulfilled locally so the shared upstream bucket pays nothing; an RTL page; and a provider-page negative control proving its toolbar does not exist at all while the scripts are held. Every filter case asserts that no sample was requested, watching REQUESTS rather than responses, because a request that is aborted or fails never produces a response to notice. A React upgrade that changes hydration will fail these.

Four things the harness taught us along the way, recorded because they will bite the next agent. A page whose scripts are held never fires DOMContentLoaded, so the navigation must wait on `commit`. Such a page produces no animation frames at all, so any helper that waits on `requestAnimationFrame` has to race a deadline or it hangs forever. Playwright's own visibility heuristic called a laid-out Firefox input hidden on that page, so the precondition waits on real geometry instead. And this build emits its stylesheets under `/_next/static/chunks/` alongside the JavaScript, so a route pattern written to hold the scripts held the CSS too and left the page unstyled: the gate filters on the request's resource type, or it is testing a different page than the one readers get.

## 2026-08-25: the sitemap renders on every request

The sitemap no longer uses the daily ISR route cache. Cloud Run keeps ISR state per instance, and sitemap traffic is sparse enough that the first requester after an instance recycle can receive the deploy-time URL set while regeneration runs in the background. The route is now force-dynamic, so its first response is generated synchronously from the current catalog. `getSite()` still keeps the built catalog in a six-hour process memo and coalesces refreshes, so this does not make every sitemap request an upstream fetch. The 3.2 MB serialisation cost is accepted at crawler traffic levels. The scheduler remains pointed only at `/api/health`, and no separate Firebase cache policy was added.
