# Architecture

How Speakshelf works, and the invariants that keep it working. Update this file in the same commit as any change that makes it stale.

## The shape

Next.js 16 App Router, classic caching model (cacheComponents is off, and stays off: `dynamicParams` on the language pages depends on it), TypeScript, no UI libraries, no Tailwind. One interactive component (`components/Explorer.tsx`, with its filter fields, its mobile filter panel and its voice row split into siblings, and two modules of its own that were extracted when it outgrew the cap: `lib/filter-url.ts` for the query-string state machine and `lib/playback.ts` for the sample player. The Explorer keeps the catalog, the filters and the list; those two keep the address bar and the sound), a small client nav (`components/MastNav.tsx`), an analytics boundary (`lib/analytics.ts` + `components/Analytics.tsx`), a server catalog library (`lib/catalog.ts`), a provider bless config (`lib/providers.ts`), two API route families, and static pages around them. Files stay small (hard cap 1,000 lines, aim far below); split along module seams before a file bloats.

## The stylesheet manifest

`app/globals.css` is the manifest, not a stylesheet: it carries no rules and imports three sheets in cascade order, `app/styles/base.css` (tokens, per-locale font stacks, reset, masthead, provider tabs, hero, sections, family tiles, tags, umbrella cards and band), `app/styles/explorer.css` (toolbar, filter fields, mobile filter panel, voice rows and their two-line shape) and `app/styles/site.css` (language suggestion, toast, consent bar, playback indicators, family note, language index, sub page header, about, footer). INVARIANT: import order is the cascade, and the manifest stays the only stylesheet imported anywhere. Two files import it, the locale layout and `app/global-not-found.tsx`, which bypasses layouts and so has to ask for it itself; both ask for the manifest, never for a sheet inside it. Two rules of equal specificity are still decided by which comes later, so moving a block between sheets, or reordering the imports, changes the rendered page; a new sheet goes where its rules already belong in the order. The split was mechanical: concatenating the three sheets reproduces the single file they came from byte for byte, minus the header comment that moved to the manifest.

## Analytics

`lib/consent.ts` + `components/ConsentBanner.tsx` show a one-time consent bar (choice stored in localStorage, no reopen UI); nothing gates on it yet, and `applyConsent` is the only place real gating may ever be added. `lib/analytics.ts` is the sole vendor boundary: nothing else imports mixpanel-browser or touches gtag. Mixpanel runs with autocapture and 100 percent session replay; GA4 loads gtag.js with a queued stub (no inline script) and gets one page_view per route change from `components/Analytics.tsx`. Page locations and referrers are query-and-hash-stripped before emission (the tts-microutil pattern): here that is pageview-dimension hygiene, since the explorer keeps filter state in the query string. Precision events beside autocapture: sample_played (with cache tier memory|cached|network, the format actually served, and the click-to-sound duration in ms), sample_failed (format where one was served, plus the reason), sample_generating, filter_changed, search_used (debounced), provider_opened. INVARIANT: the reported format is derived from the server's `contentType`, never from what this browser asked for, and is omitted when the type is unrecognized: a preference is not evidence of what arrived. It is remembered per voice so replays out of the blob and decoded tiers report the format they are actually playing. Always-on by the owner's decision; their legal owns the consent posture (see decisions). Ids live in `.env` as NEXT_PUBLIC_ vars, baked into the client bundle at build, public by nature.

## Security headers

`next.config.ts` sets on every route: X-Frame-Options DENY, nosniff, Referrer-Policy strict-origin-when-cross-origin, COOP same-origin, Permissions-Policy denying microphone/camera/geolocation, plus HSTS and a CSP in production only (dev needs HMR's unsafe-eval). CSP notes that matter: `script-src 'unsafe-inline'` is load-bearing for the pages' inline JSON-LD and for the locale-select script in the global 404's head, not just analytics; `style-src 'unsafe-inline'` covers next/font's injected font-face styles; `worker-src 'self' blob:` and the mixpanel hosts carry session replay. Sample audio hosts are an allowlist in connect-src (blob warm fetch) and media-src (the audio element): GCS today plus Cloudflare R2 (`*.r2.dev`, `*.r2.cloudflarestorage.com`) pre-added for the owner's planned move. INVARIANT: if the AI TTS Microservice starts minting sample URLs from any other host (a custom domain included), production playback is CSP-blocked until next.config.ts adds that host; `/api/sample` warns in the server log the first time it sees an unlisted host, so watch for `sample audio host` warnings. `connect-src` also carries the whole `https://www.google.com` origin: gtag posts GA4 beacons to `https://www.google.com/g/collect`, and the owner chose the origin over a path-scoped entry for robustness against Google's beacon routing (ruled 2026-08-16; the history of the blocked beacons is in decisions). Verified against a production build: playback, replay recording and every beacon, GA4 included, run with zero CSP violations.

## The provider dimension

Everything is generic over providers; going live is not. The split is deliberate:

- **Machinery is generic.** Data (`packed v4` keyed by provider), routing (`/[provider]`, `/[provider]/voices/[lang]`), playback (voice ids carry the provider prefix), sitemap, llms.txt and metadata all iterate the blessed set. Nothing anywhere hardcodes "google" except redirects for the pre-umbrella URLs.
- **Going live is a blessing.** `lib/providers.ts` is the one place a provider becomes real: key, display names, hero and about copy, the word it uses for its voice groupings ("model families" for Google, "engines" for Polly), plus per-provider family metadata in `lib/families.ts` (family keys collide across providers; both Google and Polly ship a "Standard"). The bare upstream `/voices` endpoint returns every provider the AI TTS Microservice carries; anything unblessed is console-logged (`catalog refresh: unblessed provider ...`) and dropped. Blessing requires honest copy and a real browser playback pass, so it stays a human act.
- **Voices are counted the provider's way.** A voice is one entry in the provider's own published voice list; a sample is one playable render. The bless config's `voiceIdentity` says which: `row` for google and kokoro (Google's list counts every language+family+name), `langName` for polly (AWS's table lists a voice once per language with engines as capability columns, so the API's per-engine rows are renders of one voice: 177 rows, 113 voices). Cross-language name reuse (Google's Achernar in 87 languages, Polly's bilingual Aditi) stays counted per language because both providers' own tables do that. The explorer still lists one row per render; only counts collapse.
- Blessed today: google (4,586 voices), polly (177), kokoro (54). `scripts/build-data.mjs` keeps its own BLESSED list in step with the config.

## Internationalization

Fourteen locales (en default, plus es, zh, hi, fr, bn, pt, ru, id, ar, sw, ja, de, it). English lives byte-for-byte at the original unprefixed URLs, an invariant; other locales are path-prefixed (/es/google), and /en variants 308 to the clean path. Arabic is right-to-left: RTL_LOCALES in i18n/locales.ts drives the html dir attribute, direction-bearing CSS speaks logical properties (the brand mark deliberately stays physical so it always matches the favicon), Latin ids and codes hold their direction via bdi and dir=ltr, each style term on a voice row is its own bdi with the separators left outside the isolates so a list of terms cannot merge into one bidi run, the sub-model options carry an explicit LTR isolate (LRI) around the RENDERED text only (a label that opens with digits, "2.5 Flash", reads as "Flash 2.5" in a closed RTL select without it) while `lib/families.ts#modelLabel` stays bare because it also feeds the search index and the mobile row's model text, the search input takes dir=auto, and the Arabic and Japanese pages load their own IBM Plex faces through per-lang token overrides in `app/styles/base.css` (Plex Mono stays first so codes render as codes). next-intl carries the machinery: `i18n/routing.ts` (defineRouting, as-needed prefix, detection off) is the only i18n module the proxy may import; `i18n/navigation.ts` (locale-aware Link/router) and `i18n/request.ts` (locale via next/root-params, messages per locale) must never be pulled into the middleware bundle, or the build breaks and pages go dynamic. All prose lives in `messages/<locale>.json`, one file per locale with identical key sets (a missing key throws at runtime); protected names never translate (voice, family, engine and provider names, Speakshelf, AI TTS Microservice, codes, ids). Language display names localize through Intl.DisplayNames; conjunction lists through Intl.ListFormat; bare comma lists a message closes itself through listNamesPlain (zh takes its enumeration comma); message-owned numbers through ICU {arg, number} (plural # also formats), directly rendered stat cells and the preformatted familiesCount through toLocaleString(locale). Every page emits a self-canonical plus the complete reciprocal hreflang set with x-default at English, mirrored in the sitemap's alternates. Browser language never redirects: a one-tap suggestion in the visitor's own language (strings in i18n/locales.ts, deliberately in the target language) offers the switch once and remembers any answer; the footer carries a locale select. INVARIANT: that offer is never in the document flow. It can only be decided after hydration, because localStorage and navigator have no server counterpart, so anything in flow arrives a beat late and displaces the page under the reader (measured at 45px on /ja and 42px on /bn before it was fixed); reserving the space instead would tax the majority who are never offered anything. Search documents rebuild per locale and carry localized and English terms side by side, so "femenino" and "female" both work. llms.txt and the OG card stay English. Analytics events keep stable English names with the locale as a dimension.

### Language label invariants

`lib/lang.ts` holds the deliberate departures from CLDR and `scripts/check-langnames.mjs` guards every one of them (run it after touching the library or refreshing data). The labels themselves sit in `lib/lang-data.mjs`, plain JavaScript so that the library and the fixture read the same file: the fixture used to transcribe all five maps, which meant a label could be corrected in the library and still be graded against the old copy. What the fixture still keeps of its own is the resolution around those maps, because the library is TypeScript and the fixture runs under bare node. the Google codes carry their proving quotes and URLs in the code, while Polly's arb and en-GB-WLS record observed runtime behavior that the fixture pins down rather than an external citation. Since the owner's ruling of 2026-08-16 every label carries a bracket in every locale, and bracket text stays short. The fixture asserts that across the whole catalog: at least one pair per label, opening and closing counts balanced, contents non-empty, in the ASCII or the fullwidth form. Nested pairs are legal outside English, because CLDR nests there itself (ru and es render Myanmar as "Мьянма (Бирма)" and "Myanmar (Birmania)" inside the label's own bracket); English additionally asserts exactly one pair with contents capped at 16 characters, so a CLDR long form coming back trips the fixture ("Hong Kong SAR China" was 19, and the longest sanctioned English contents today are "Modern Standard" and "North Macedonia" at 15). Google's `ar-XA` and `ar-001` are one register under two codes, which Google's own voices doc states, so they share one hand-localized "Arabic (Modern Standard)" in all fourteen locales and their codes tell them apart: the mono code chip on group heads and language page heroes, a code suffix on the Explorer's dropdown option (inside an explicit LTR isolate, so an Arabic option line cannot reorder it), the code beside a twin's name in the provider page's language grid, and the code in each twin page's metadata title, share title and JSON-LD name. Because they share a name, the fixture's uniqueness check carries a group-exact allowance: a shared name passes only when the complete same-name group is exactly {ar-001, ar-XA}, so a third code joining that name still fails, and the twins are separately asserted equal in every locale and distinct from arb and ar-EG. Polly's `arb` keeps its own hand-localized "Arabic (Standard)", because CLDR collapses it onto plain Arabic and the umbrella home page names it as a Polly-versus-Google variant. Google's `jv-JV` carries Google's own "Javanese (Java)", hand-localized in all fourteen, since CLDR prints the raw subtag as "Javanese (JV)". Polly's `en-GB-WLS`, which Intl cannot render in any locale, is hand-localized like the other exceptions; there is deliberately no English fallback layer, so an English string cannot leak into another locale, and a future code Intl cannot render gets its own hand map (until it does, it renders as its raw bracketless code, which the fixture flags). English alone shortens five long region names, US, GB, Hong Kong, Myanmar and UAE; every other locale keeps its full CLDR names. All of this is display only: the codes in the data never change, and English URLs stay code-based.

## Catalog data flow

1. `lib/catalog.ts#getSite()` is the single entry point. `livePacked()` fetches the bare `GET /voices` (all providers, one call), groups by the `provider` field, drops unblessed providers with a warning, and packs the rest.
2. Validation before adoption: every voice id must be reconstructable as `{provider}:{language}-{Family}-{Name}`, and each blessed provider present in the committed fallback must come back at 80 percent strength or the whole fallback is used. A provider blessed before its first data refresh has no yardstick and passes on live data alone. Every rejection logs a `catalog refresh` warning.
3. `data/voices.packed.json` (version 4) is the committed seed and fallback: `{providers: {key: {models, voices}}}` with one tuple per voice, `[language, family, name, gender(f|m|n|u), tier(p|u), stylesCsv, traitsJson?]`. The optional seventh slot carries non-style characteristics exactly as the API keys them (age, pitch, accent, use_case, roles) and only when non-empty: Polly's child voices and Google's per-voice pitch ride there today, and Azure's roles will land without a format change. The UI currently surfaces `age` (the gender cell reads "female (child)", searchable); the rest is retained data, served by /api/catalog, awaiting a designed use. `scripts/build-data.mjs` regenerates it in one API call.
4. The all-provider response is about 2.9MB, which is over the Next data cache's 2MB item limit; the fetch cache stores nothing (the build logs "items over 2MB can not be cached"). The process memo is therefore the effective cache: the built site (per-provider catalogs, site-wide byId, umbrella stats) is held six hours per process, keyed by source (live or fallback) plus date and count. `/api/sample` uses a fresh-floor variant (`getSiteFresh`, 60s) when an id misses, so a voice that appeared upstream is playable without waiting out the memo; the floor keeps id-guessing from becoming an upstream fetch storm.

Pages export `revalidate = 86400`. The two dynamic routes take opposite `dynamicParams` postures, each for a reason. `/[provider]` keeps `dynamicParams = false`: this route is ISR, and Next persists an on-demand `notFound()` render as a cached negative entry per URL, which on Cloud Run lands on tmpfs and counts against the instance's memory; with `false`, an unknown one-segment path never renders here and is answered at the routing level by the global 404, which caches nothing per URL (verified against a production build: garbage one-segment paths 404 branded, `/google` stays prerendered). `/[provider]/voices/[lang]` keeps `dynamicParams = true` out of necessity, so a language newly appearing in a data refresh renders on first request; the cost, accepted and bounded, is that garbage under a real provider's `/voices/` prefix writes a small cached negative entry with the daily revalidate, on an instance filesystem that recycles with the instance.

Sub-model lists ride the same pipe: each provider's `models` map is built from `available_models`. Google's Gemini is the only multi-model family today; the Explorer's control is generic (first family with more than one model) so a second one just works.

## Routing and redirects

- `/` is the umbrella homepage: provider cards, aggregate stats, about. No voice list.
- `/{provider}` is a full provider home: hero with section jump links, family tiles, language grid, about, voice list last.
- `/{provider}/voices/{lang}` are the SSR language pages.
- Google lived at the root before the umbrella. `next.config.ts` issues permanent redirects (Next answers **308**, the method-preserving permanent code): `/voices/:lang` to `/google/voices/:lang`, and `/` to `/google` when any explorer query param is present. `has` entries AND together, so that second rule is four rules, one per param (family, language, gender, gmodel); `q` is deliberately not redirected (too generic to bind to /google forever with a permanently cached redirect); query strings pass through automatically.
- Masthead nav (`MastNav`, client, `usePathname`) is global provider tabs with the active provider underlined. Section wayfinding lives in each page's hero jump links, so the masthead never needs to know a page's sections.
- Scale caps, so twenty providers can never break chrome or copy: the masthead names at most four shelves (past that: three plus an "All providers" link), the umbrella hero names at most three as a bare comma list and its message closes with its locale's "and more", cached share lines always name two plus "and more" (one provider: just its name, no claim of more).
- Unmatched paths get the branded, translated 404 at `app/global-not-found.tsx`, answered at the routing level. `experimental.globalNotFound` in `next.config.ts` turns it on; the flag is experimental in 16.3 and gets re-checked at every Next upgrade. Next skips rendering entirely for a URL that matches no route and serves this file, which is why it is the only 404 here a reader without JavaScript can see: the markup is in the HTML body, not in an RSC payload. It bypasses every layout, so it carries its own `<html>`, imports the fonts from `app/fonts.ts` (extracted from the locale layout so both entry points share one next/font call site and one set of files) and imports `app/globals.css`, the same manifest the layout imports. The old `app/[locale]/[...rest]/page.tsx` is gone: routing now declines `/a/b/c` on its own, so nothing renders and nothing is cached. `/[provider]` keeps `dynamicParams = false` and its refusal is what sends `/garbage` here. No ISR negative entry is written, which was already true of the catch-all it replaces; what is new is that nothing renders at all, since the global page is prerendered once at build and served from that copy with `Cache-Control: private, no-cache, no-store` (measured before and after against a production build of each).
- One document serves all fourteen locales. Every locale's block is server-rendered as a sibling `div.nf-v[data-l]` carrying that locale's `lang` and `dir`, and `app/styles/site.css` shows only the block whose `data-l` matches the `html` element's. A tiny parser-blocking inline script in the page's own `<head>` reads the first path segment and, for the thirteen prefixed locales, sets `data-l`, `lang` and `dir` on `html` before the first paint; the CSP already allows inline script for the JSON-LD blocks. Its code list is written out longhand: no translated string and no request-derived value may ever enter a script tag. Without JavaScript the server defaults stand and every reader gets the English block, branded and readable, which is the trade the design accepts. The document title is English in all fourteen for the same reason: one document has one title, and no translated string may ride in the script that could swap it. Adding a fifteenth locale means editing three hand-kept copies of the locale set, the code list in that script, its rtl test, and the rules in `site.css`; the blocks themselves come from `LOCALES`. All three fail silently when they drift, an unknown locale rendering as English, as a blank page, or in the wrong direction, so `scripts/check-404-locales.mjs` asserts all three against `i18n/locales.ts` (run it after touching any of them). Without JavaScript an Arabic reader gets the English block and its links point at the English home, so the fallback costs the locale, not only the language of the sentence. The page is deliberately a shell: masthead wordmark, heading, body line and a link home, in that locale. No provider tabs, no language suggestion, no locale switcher, no analytics, no consent bar and no footer, because none of them can run outside the layout that owns their providers and none is worth a second copy on a page whose job is to point back at the shelf.
- A route that renders and then calls `notFound()` is the other half, and it does not reach the global page. `app/[locale]/not-found.tsx` stays for it: measured against 16.3.0, `globalNotFound` covers URLs that match no route only, since `createNotFoundLoaderTree` is reached from the server-action path alone, and a `notFound()` thrown mid-render still produces Next's own `<html id="__next_error__">` document with an empty body and the branded markup in the RSC payload, rendered on the client. Deleting the locale-scoped file would swap that payload for Next's unbranded "404: This page could not be found". One shape of URL takes this route today: garbage under a real provider's `/voices/` prefix, because that segment must stay `dynamicParams = true` for data refresh. Every other garbage shape reaches the global page instead, and the proxy matcher is what makes that true: `proxy.ts` excludes by exact segment (`api/`, `_next/`, the five named files anchored with `$`), so `/foo.txt`, `/apiary` and `/_nextfoo`, which the old prefix-and-blanket matcher let skip the middleware and land in the app tree as garbage "locales", now go through the locale rewrite and are declined by `[provider]`'s `dynamicParams = false` at the routing level (measured: all branded, no error document, no ISR entry). `public/` holds only og.png; a new public file needs its own matcher entry. Do NOT try the other route to the same goal, `dynamicParams = false` on the locale layout: measured on 16.3.0, a layout-level `false` cascades over the voices page's explicit `true` (`.next/prerender-manifest.json` flips that route to `fallback: false`), and a language newly appearing in a data refresh would 404 until the next deploy. The crawler-facing signals, the 404 status and the injected `noindex`, are correct on every shape either way.

## Sample playback

Samples are never synthesized here and never cost credits. The upstream `sample-url` endpoint mints a signed 24 hour GCS URL, generating the sample on first request (202 with `retry_after` while it works). Verified for all three providers in a real browser.

Server, `app/api/sample/route.ts`, in order:

1. Per-IP token bucket (`lib/ratelimit.ts`): burst 30, then 30 a minute, answers 429 with Retry-After. A sanity guard on the one non-static route, generous enough that a person never meets it; x-forwarded-for is spoofable, so it is not security. The shared upstream budget (~1000 sample-url calls a rolling hour) is protected by the next layer, not this one.
2. Voice id validated against the site-wide byId map (all providers), with the fresh-floor refetch on miss; optional `model` validated against that voice's provider models map.
3. Optional `formats`, an ordered preference the browser states (`lib/audio-formats.ts`). Anything outside `opus,aac,wav` is refused with 400 here and never forwarded, so a bad list cannot become an upstream call. Absent means the historical WAV.
4. Signed URLs cached and coalesced under `id|model#formats`, because a ready URL is format-specific: one server cache serves a Safari visitor asking for AAC and a Chromium visitor asking for Opus, and sharing an in-flight lookup between them would hand one of them audio it cannot play. INVARIANT: never coalesce ready lookups across different format preferences.
5. The "still generating" answer is kept in a separate map keyed by voice and sub-model but not format, because synthesis is format-independent upstream (one sample per voice, converted to the other formats afterwards). Every retrier of a cold voice therefore coalesces into at most one upstream lookup per retry interval and one miss token, whatever format it wants. INVARIANT: that marker is consulted only on a genuine cache miss, never ahead of a ready URL. A voice can be mid-generation for one format while another format's URL is cached and playable, and answering that reader "still preparing" would hold a ready sample back for the marker's whole life. A ready answer also clears the marker, since generation has demonstrably finished.
6. Cache lifetime comes from upstream's absolute `expires_at`, minus an hour of safety, capped at a 20 hour ceiling for an upstream that ever stops reporting it. The response carries that moment as `reuseUntil`, and the browser expires its own copy against the same moment: INVARIANT: no layer restarts an expiry clock from when it received a URL, because a URL handed over late in its life would otherwise be treated as fresh by everything downstream and die in a long-lived tab.
7. A request that asked for a compressed format and got `audio/wav` back is cached ten minutes only. That answer means the conversion task has not produced the preview yet, and holding it a full day would pin the voice to the large file long after the small one landed. Scope: this governs the next lookup, not the tab. A voice already played keeps its bytes in the blob and decoded tiers for the session, so that reader's replays stay network-free on the WAV rather than being upgraded.
   The generating marker's coalescing has one bounded exception, left as it is: before the first 202 installs the marker, two different formats asking for the same cold voice in the same instant each start a lookup. Serializing that would block one reader behind another's format to save at most one token.
8. `{url, reuseUntil, contentType}` on success; upstream 202 relayed as `{status:"generating", retry_after}`; upstream 429 mapped to 503 with Retry-After.

Client, in `lib/playback.ts` (the `usePlayback` hook the Explorer mounts): `play()` resolves the decoded tier first (`lib/audio-replay.ts`: AudioBuffer LRU played through a singleton Web Audio context, a synchronous memory hit with no media element and no network, the same decoded-memory path on every engine, resumed on the click when a backgrounded tab suspended the context), then the blob cache (module LRU of object URL plus raw bytes, media-element playback). INVARIANT: the decoded tier plays only through a context that reports itself RUNNING. iOS creates an audio context suspended unless a gesture is in hand, adds an `interrupted` state of its own after a call or another app takes the session, and `resume()` is a promise that can hang, so a source started before it settles is silence behind a moving equaliser. A context that is asleep is woken and re-checked with a 1.5s deadline; one that will not wake is a tier MISS, not a failure, and the play falls through to the blob below, which needs no context at all. The decoded bytes are kept, since the fault is activation and not the audio. INVARIANT: nothing creates that context before the first sound of a session. Decoding belongs to confirmed playback for exactly this reason: building it earlier, inside a fetch, is how a first play succeeds through the media element and every later replay goes silent, then the URL cache (held until the server's `reuseUntil`, with the old 18 hour span kept only for a server that reports none), then `/api/sample` carrying this browser's format preference (`lib/audio-formats.ts`: Safari asks for AAC then WAV since it decodes AAC in MP4 natively, every other engine asks for Opus then AAC then WAV, probed once per session with a media element; WAV always ends the list because it always plays) on a 90 second wall-clock patience budget measured from the reader's tap (the row hands `play()` its own click timestamp, so the clock is the reader's wait and not the network's; the URL cache's own freshness check stays on real wall clock against the server's absolute deadline): 202s retry honoring `retry_after` (clamped 4 to 15 seconds, "preparing sample"), transient failures (404 before the trigger registers, 5xx mid-render, timeouts) retry as bounded blips instead of claiming absence, every request carries a 15 second abort deadline, and exhaustion says "still preparing" whenever a 202 was ever seen; "sample unavailable" is reserved for chains that never saw generation. The server keeps a generating marker per voice for its retry interval, so concurrent retriers of a cold voice coalesce into one upstream lookup per interval. How the bytes reach the player depends on the format actually served, not on the browser. A compressed sample (opus or aac, tens of kilobytes) is FETCHED WHOLE and played from an object URL: one request, and those same bytes fill the blob tier immediately and the decoded tier once playback is confirmed. This is a WebKit fix that showed no measured penalty for the other engines: a media element handed a URL opens several range requests before it will start, and WebKit made four per first play where it now makes one. Measured end to end on production, a first play in WebKit went from a median of 4050ms to 2126ms. An alternating same-session test of the two transports found Chromium and Firefox indifferent (452ms against 425ms, and 444ms against 443ms), so the choice is made by format rather than by browser: no engine showed a penalty for taking the same path. The WAV fallback keeps streaming, where progressive playback of a 460KB file is worth more than one-request efficiency, and an unrecognized content type streams too. Streamed plays still warm afterwards, at the first playing signal, in-flight deduplicated, decoded from the stored bytes (never `fetch(blob:)`, which sits outside connect-src). INVARIANT: a play that fetched its own bytes must never warm again afterwards, or the second transfer this design removes comes straight back. INVARIANT: every way an object URL can fail, the element's error event, the media deadline, and a play() rejection that is not an autoplay refusal, routes through ONE guarded recovery that drops the suspect blob, disowns its decoded buffer AND any decode still running for it, and streams: the URL it holds when that is still fresh, otherwise a newly minted one, because a blob outlives its signed URL as a matter of course and the reader should not be told the sample is gone. Everything after that recovery streams, so a fresh URL cannot rebuild the blob that just failed. It is guarded because a second attempt would rebuild the blob that just failed; it is shared because a blob that fails any other way would otherwise leave the reader with no audio at all, where the old streaming path would have played. Preparation steps that fail without costing the reader their sample, a bytes fetch that fell back to streaming or a decode that only powers the next replay, are reported as `sample_prepare_failed` and never as `sample_failed`: counting them there would report successful plays as failures. They are deduplicated per voice per session. No speculative prefetch ever, the shared sample-url bucket is not spent on guesses. Replays are network-free on every engine. They are also immediate whenever the audio context is already running, which is the ordinary case once a session has made a sound; a context that has to be woken costs up to the 1.5s deadline, and one that will not wake falls back to blob playback through the media element, which is slower still but audible, and measured at 3.9s in Chromium and 5.7s in WebKit against a context that never wakes at all. The active Web Audio source is stopped before any new play, on stop and on unmount, so a switched voice never sounds underneath the next one. A `playGen` counter guards every async step against stale callbacks; `ontimeupdate` marks playing where Safari fails to fire `onplaying`; a dead object URL falls back to the network once; a failed signed URL is dropped from cache. The startup phase carries ONE absolute deadline (20 seconds, clamped to what is left of the reader's budget), set on the first attempt and never renewed. INVARIANT: whole-byte fetch, object-URL startup, the streaming fallback, and a recovery that has to mint a fresh URL all draw on that single window, including that lookup's own abort and any retry it schedules. Fetching bytes and starting a media element are different mechanisms but one wait to the reader, so a fetch that fails fast hands the unspent time to the stream that follows, and a fetch that burns the window leaves none. INVARIANT: every wait the chain can schedule, the retry interval, the request abort and this deadline, is clamped to the remaining budget, so the ninety seconds are genuinely terminal. Without the media deadline nothing bounded the load at all, since the lookup's abort covers only the URL request: an element that neither starts nor errors, which is what a stalled range request looks like, left the row spinning for good. On expiry the element is paused and its handlers dropped so a late event cannot contradict the failure, the suspect URL or object URL is evicted, and `markPlaying` refuses to run once an attempt has failed.

Rows are memoized (`components/VoiceRow.tsx`) with a comparator over voice identity, provider, labels and the state object's contents, and the list hands every row ONE shared `onPlay` rather than a closure each. A big provider holds thousands of rows under the component that owns playback state, so without both, changing one row's state reconciled all of them; measured on the Gemini filter, this cut a filter change from 2.95s to 1.66s and its worst main-thread block from 386ms to 139ms. Virtualization is deliberately NOT used: the list is sectioned per language with sticky heads and `content-visibility` containment, which a fixed-height windowed grid would fight. 429 and 503 both show "busy, try again in a minute". Cache keys are full voice ids, plus the chosen sub-model where a family has several, so providers and sub-models never collide.

## Page structure invariants

- Provider pages render hero, families, languages, about, and the voice list LAST. The list loads client side, grows by tens of thousands of pixels, and keeps re-measuring under `content-visibility: auto`, so every anchor target must sit above it. Do not move sections below the list.
- Language pages server-render their rows for SEO through `ExplorerList` (no `useSearchParams`). Provider pages wrap `Explorer` in Suspense because `useSearchParams` client-renders up to the nearest boundary. Keep that split.
- `.explorer` carries both its own class and `.shell`; it must only use longhand padding so the shell's side gutters survive. The toolbar grid has 5, 4 and 3 column variants driven by which filters apply; the family filter label uses the provider's own word (ENGINE on /polly).
- Under 721px the Explorer takes a different shape and drops nothing. The toolbar keeps the search field alone; the selects move into `components/FilterPanel.tsx`, a full-screen boxed dialog opened by the FILTERS button, which fills its own row on the results line and pushes the count and clear-all onto the line below it (count at the start, clear-all at the end, as on desktop). Its badge counts the select filters only (never the search query, which stays visible in its own field, and never a route-locked language). The fields are one component, `components/FilterFields.tsx`, mounted twice with an id prefix per mount, so the document never carries two `#f-family`. The panel is a real dialog: role, aria-modal, its name from the panel title, initial focus inside, hand-rolled focus containment (no dependency), Escape and a close button, focus restored to the trigger, and a body scroll lock that saves the prior overflow value and restores it on close and on unmount. A window widened past the breakpoint closes the panel rather than leaving a modal over the desktop toolbar. Rows go two-line (`components/VoiceRow.tsx`), in the owner's 2026-08-16 order: line one is the play button, the name, the styles and the gender at the line end, which is how the desktop row reads; line two is the family tag, the effective sub-model and the trait tag, indented to the name's edge because the play button's tap target spans both lines while its 32px look is unchanged. A transient generating or error note takes line two while it shows and the metadata returns when it clears. The break between the lines is a full-width `.vrow::after` pseudo element ordered between the two groups (never `.play::after`, which owns the tap strip), and it is 4px tall while the row gap is zero: a break line of its own sits between two row gaps and would double the spacing, and a negative margin cannot cancel one of them, because a flex line's cross size does not go below zero (measured in Chromium). Every rule of this shape lives in a media query: from 721px up the Explorer is exactly what it was. One label rule reaches both widths: the language dropdown appends the code to an option when another code of that provider localizes to the same name (see the label invariants above).
- `.search-input` and `.select` reach 16px under `@media (max-width: 720px), (pointer: coarse)`. iOS Safari zooms the page into any focused control under 16px and never zooms back. Do not solve it with a viewport `maximum-scale`, which disables pinch zoom for everyone, and do not widen the rule into a global input font size: only these two controls take a touch keyboard.
- Search is client-only through `lib/search.ts`: one document per voice built from every field and trait (future traits searchable by construction), token-AND queries, word-start matching for plain tokens (so "male" never matches female), whole-document substrings for separator tokens (voice-id pastes), diacritics stripped. INVARIANT: no bidi isolate (U+2066..U+2069) may reach a search document. Isolation is a render-site concern; a control character inside a document would silently break a substring match on a voice id or a model name. Fuzzy matching is deferred until search_used analytics show zero-result typos.
- `.fam-grid` follows the tile count below five columns (`fam-grid-4` … `fam-grid-1`) so providers with few families show no dead cells.
- Overlay stack, lowest first: sticky language group heads 10, masthead 20, language suggestion 30, family toast 40, consent bar 50, mobile filter panel 60. A new overlay takes an explicit place in that list rather than an arbitrary number. INVARIANT: no two of them may share a slot. The suggestion is the standing offer and holds the top corner; the toast is transient and yields, dropping below it through `body:has(> .lang-suggest)` above 520px and, under it, preferring the bottom edge unless the consent bar has already taken the bottom (`maybeToast` in `lib/playback.ts` reads both). `:has()` is load-bearing here because the suggestion is mounted by the locale layout and the toast by the playback hook, so no shared class or sibling selector reaches both; the child combinator keeps the match to body's own children. The offsets are measured, not guessed: the suggestion's bottom edge reaches 119px wide and 137px narrow across all fourteen locales in Chromium, WebKit and Firefox. Anything moved here is re-measured, including the `scroll-margin-top` that keeps an in-page jump from landing underneath the suggestion. That one applies at every width, not only where the suggestion spans the page: the corner card does not clear the section headings horizontally the way it appears to, reaching 387px into their line at 721px and still 44px at 1024px, so the jump is pushed below it rather than argued about per width. Overlapping the hero at the top of the page is accepted and intended, as it is for the toast: these are notifications, and the alternative is the layout shift this replaced.
- Language pages ship the whole Explorer toolbar in the server HTML, so a reader can type or choose before React attaches, and those interactions are not lost: React 19 leaves a live input or select alone while hydrating (`initInput` takes `isHydrating` and skips the value assignment; the select hydration branch never calls `updateOptions`), so the browser still holds the choice and only the component's state is behind. INVARIANT: `ExplorerCore` adopts those live values once, in a layout effect, as a single state update scoped to the server-rendered toolbar. One update not because separate calls would clobber each other, they would not, `patch` merges functionally, but because the toolbar's fields are one answer and reading them together is the only version that does not depend on batching or on the order effects happen to run in; a layout effect because refs attach at commit and it runs before the next paint, so no controlled re-render can enforce the stale state first; scoped to the toolbar because the mobile panel cannot exist yet, its opening click needing the React that has not arrived. The sub-model picker shows the first sub-model when nothing is chosen, so that value normalizes back to the empty default. A route-locked page renders no language select, so there is nothing to read there; the language value is read when the select does exist, so an unlocked list mount is covered rather than quietly half-served. Provider pages build the toolbar with React itself and have nothing to recover, so this never runs on them. This leans on pinned React 19 behavior rather than a documented API promise, which is why the held-chunk regression test matters on every React upgrade.
- URL state on provider pages: `?family=`, `?language=`, `?gender=`, `?gmodel=`, `?q=`. The binding lives in `lib/filter-url.ts` (`useFilterUrl`), not in the Explorer, because it is a state machine and running it as two loose effects in a component is what broke it. INVARIANT: the URL and the filter state are never allowed to drive each other. One string records the query both sides agree on; a router navigation is adopted only when it differs from that string, a `replaceState` happens only when the state differs from it, and anything equal to it is our own echo (Next mirrors an external `replaceState` back into `useSearchParams`) and is dropped. Three further rules hold the machine together: the URL is parsed during the FIRST render through a lazy state initializer, never applied by an effect afterwards; the writer stands down for exactly one pass while an adopted navigation is still landing, which is sound because the writer's dependencies are a superset of the adopter's so that pass always happens; and a write is skipped when `pathname + search + hash` already reads that way. A family or language the catalog disowns is cleared by derivation (`clampToCatalog`), never by a correcting effect: the raw snapshot still holds whatever the URL said, but a rejected value is never exposed as an effective filter and never written back to the address, so no render shows the wrong list and the writer cannot republish it. A field the reader changed while the catalog was loading survives, because the clamp only ever clears what the data denies. The adopter does write a whole snapshot, but only for a router navigation the reader themselves caused, where the incoming URL is meant to win. The hash is preserved on every write. On language pages `paramsKey` is undefined and none of this runs.
- Navigation scrolling is app-owned. `i18n/navigation.ts` is the only place to import `Link` from (never `next/link`, never `i18n/navigation-base.ts`): it wraps the next-intl Link with Next's scroll off, glides same-document destinations immediately, and records a glide intent for the rest, which `components/ScrollGlide.tsx` (mounted once in the locale layout, behind Suspense) consumes on the first route commit, gliding only when that commit matches the intent's URL, animating to the hash target or the top (`lib/glide.ts`). Back/forward, Explorer's `replaceState` writes and the locale switchers record no intent and therefore never scroll; note that Next mirrors external `replaceState` into `useSearchParams`, so never key scrolling off route changes alone. The html element keeps `data-scroll-behavior="smooth"` and the CSS smooth rule stays: native in-page anchors animate, and any navigation that bypasses the wrapper lands instant and correct. Never add `scroll-padding-top` on html (the router's in-viewport check reads it and navigations land short); offset anchors with per-target `scroll-margin-top`. Reduced motion gets instant scrolls via the media query in `app/styles/base.css`.

## SEO and agent surface

- Metadata, Open Graph and JSON-LD counts derive from the catalog at render time. Titles are unique per provider and language ("Amazon Polly English (Wales) voices"); the root is the umbrella.
- `app/llms.txt/route.ts` regenerates daily: provider list with counts, the id pattern, the packed format, the sample endpoint's 202 behavior.
- `app/robots.ts` allows `/api/catalog` (which prefix-covers the per-provider slices) and `/api/sample`, disallows the rest of `/api/`.
- `app/sitemap.ts` lists the umbrella, each provider home, and every language page (2,072 URLs today across the fourteen locales). It declares `revalidate = 86400` like every other catalog-derived route: a generated sitemap is a cached route handler, and without its own window it is prerendered once and served from that artifact until the next deploy, freezing the URL set to the catalog the build happened to see. INVARIANT: it emits no `lastmod`. The only date on hand is `site.updated`, which `lib/catalog.ts` stamps on a successful refresh rather than on a real change, so publishing it would date all 2,072 URLs to the same day whether or not anything moved; lastmod is optional and an absent signal beats a misleading one.
- `/api/catalog/[provider]` serves each provider's packed slice (force-static, daily, prerendered for the blessed set). Per-provider on purpose: google is about 95 percent of the payload and the smaller shelves should not pay for it.

## Caches at a glance

| Layer | Where | Lifetime |
| --- | --- | --- |
| Voice list fetch | Next data cache | refused: payload over the 2MB item limit |
| Built site memo | server process | 6 h (60 s floor for miss-triggered refresh) |
| Signed sample URLs (per voice, sub-model and format) | server process map | upstream expiry less 1 h, capped at 20 h; 10 min when a compressed request fell back to WAV |
| Signed sample URLs | client module map | the server's `reuseUntil`; 18 h only if none was sent |
| Sample audio blobs (object URL + raw bytes) | client module LRU | session, 24 entries; a compressed play fills this before it starts, a streamed one after it succeeds |
| Decoded sample audio (AudioBuffer) | client module LRU | session, 10 buffers |
| Rate limit buckets | server process map | idle-swept after 10 min |
| ISR page cache | instance disk | per instance, dies with the instance |

## Deployment

- Cloud Run runs `next start` in us-central1 at min 0, max 1 instances. One
  instance is deliberate: the signed-URL cache and both rate buckets are
  process-local, so horizontal scale would multiply the upstream miss budget.
  Scale-to-zero means a cold start of a second or two for the first visitor
  after an idle spell; a Cloud Scheduler probe hits `/api/health` on the
  run.app URL every five minutes (bypassing the CDN on purpose) to keep one
  instance warm most of the time. The probe route calls `getSite()` so the
  catalog memo warms with the process. Best effort, not a guarantee.
- Classic Firebase Hosting fronts the service at https://speakshelf.com
  (www 301-redirects to the apex, path and query preserved) with managed TLS
  and Google's CDN, through a single catch-all rewrite to the Cloud Run
  service; the stub public dir must stay empty of deployable files or they
  shadow the rewrite. DNS lives at Cloudflare, records DNS-only, never
  proxied. A new Hosting release purges the CDN cache; after a canonical
  rebake redeploy, ship a Hosting release too or day-long s-maxage keeps
  serving the old HTML.
  Firebase App Hosting is a different product and is not used. Cloudflare, if
  the domain lives there, holds DNS records only.
- The locale cookie is off (`localeCookie: false` in `i18n/routing.ts`):
  nothing reads it with detection off, and a Set-Cookie on prefixed-locale
  pages would have made 13 of the 14 locales uncacheable at the CDN.
- ISR state is per instance and dies with it, so a fresh instance serves
  build-time HTML until pages revalidate. Accepted for a daily-refresh
  catalog; no shared cache handler.
- `TTS_API_KEY` reaches the process only through Secret Manager. Public
  `NEXT_PUBLIC_*` values bake at build time via `--set-build-env-vars`, so
  the canonical origin is the web.app site until speakshelf.com attaches,
  then one redeploy rebakes it.
- `.gcloudignore` includes the whole `.gitignore`, so env files and the key
  never upload with a source deploy.
